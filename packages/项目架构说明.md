# 项目架构说明

> 一条消息的完整生命周期(逐步 + 设计动机)见 [Chatflow.md](Chatflow.md)。

多个项目协同构成「对话式 AI 助手 + 业务操作」系统:
Vue 前端 → NestJS 网关(唯一用户权限权威)→ ai-service(Agent 编排)
→ Java model-gateway(唯一模型出口)→ 上游模型提供方;外加独立的 eval 评测包。

## 总览

```
浏览器 (http://localhost:6012, my-vue-app-ts, 业务对话端)
   │  /api /v1 代理(Vite)→ JWT 鉴权
   ▼
浏览器 (http://localhost:6013, ServerManegeUI, 管理端)
   │  /api /v1 → model-gateway(6015); /nestjs → NestJS(6011)
   ▼
NestJS 网关 (6011)
   │  ├─ 对话请求:X-Service-Key + X-User-Id + X-Username 内部鉴权转发
   │  └─ 业务接口:users/departments/job-levels/perm-config/audit
   ▼
ai-service (6010, FastAPI + LangGraph)
   │  ├─ Agent 路径:守门子图(已移除) → ReAct 循环(决策→工具→回答)
   │  └─ 直答路径:纯模型转发
   ▼
Java model-gateway (6015, Spring Boot,唯一模型出口)
   │  内部服务密钥鉴权(X-Service-Key / Bearer),X-Channel-Key 渠道路由,
   │  限流/熔断/计量(invoke_logs)/渠道管理/数据看板
   ▼
上游模型提供方 (company / 百炼,真实 key 只配置在网关 channels 表)
```

职责切分(2026-08 重构,消除团队/资产/旧角色权限体系):
- **NestJS = 业务网关 + 唯一用户权限权威**:JWT 签发;用户/部门/职级/两维权限
  (职级批量绑定 + 个人逐项覆盖)/审计的写操作规则引擎;model-gateway 只校验
  NestJS 签发的 JWT 并解析权限码。
- **Java model-gateway = 模型出口网关 + 限流熔断/调用日志**:不持有用户权限语义,
  `/api/**` 用 NestJS JWT 解析 `isSuperAdmin` 与有效权限码;5 个受控接口分别校验
  `super` / `log:view` / `policy:manage`。
- 计量唯一来源:model-gateway 的 invoke_logs(+ /api/stats 看板)。

数据存储:
- **MySQL `ai_agent`**(NestJS 管):users / departments / job_levels / permissions /
  job_level_permissions / user_permissions / audit_logs;ai-service 的 `DATABASE_URL`
  也指向它——会话与展示消息、RAG 文档与分块向量同样持久化在这里
  (`DATABASE_URL` 缺省时退回本地 SQLite `ai_service.db`)。
- **SQLite `ai-service/checkpoints.db`**:LangGraph checkpoint——**推理上下文的唯一权威**
  (全量消息含 tool 中间态);删除会话时经 `adelete_thread` 联动清理。

会话持久化**双轨各司其职、所有权在服务端**(2026-08 重构):
checkpoint 管推理,messages 表管展示(human/ai + attachments/flags/created_at);
前端只发本轮新消息,用户/助手消息都由服务端在聊天流程中统一落库——
不再由前端逐条持久化、不再全量重发历史做服务端去重。详见「四、核心流程 6」。

## 一、my-vue-app-ts(业务前端,6012)

| 目录 | 作用 |
|---|---|
| `src/view/AgentMode/` | Agent 对话主界面:`mixin.ts` 是核心交互逻辑(裸 fetch 消费自定义 SSE),`index.vue` 渲染消息/思考面板/工具步骤/各类卡片;只保留通用工具 + RAG |
| `src/view/userMode/` | 普通对话模式 |
| `src/view/Login/` | 登录(JWT) |
| `src/axios/sse.ts` | `fetchSSE`:SSE 解析器,按 event 分发回调 |

> 用户管理/资产管理页已随旧权限体系移除;业务操作通过对话式 Agent 或管理端完成。

## 二、ServerManegeUI(管理端前端,6013)

| 目录 | 作用 |
|---|---|
| `src/views/Users/` | 用户管理:显示部门/部门职位/职级,新增/编辑/删除 |
| `src/views/Departments/` | 部门管理:部门树 + 成员职位 |
| `src/views/Permissions/` | 权限维护:职级批量绑定(Tab1) / 个人单独绑定(Tab2) |
| `src/views/Channels/` | 渠道管理 |
| `src/views/Logs/` | 调用日志 |
| `src/views/Policies/` | 限流熔断策略 |
| `src/router/index.ts` | 路由权限:按 `isSuperAdmin` 与有效权限码控制访问 |
| `src/stores/auth.ts` | 登录会话 + 有效权限码缓存(`hasPerm`) |

菜单/路由按权限码渲染;调用日志需 `log:view`,限流熔断需 `policy:manage`,用户/部门管理
需 `dept:member`/`dept:info`;权限维护中职级批量绑定仅超管,个人单独绑定需 `dept:member`
且职级高于目标(超管本人不可修改)。

## 三、NestJS(网关 + 业务后端,6011)

| 模块 | 作用 |
|---|---|
| `auth/` | 登录、JWT 签发与校验(`JwtAuthGuard`)、权限码守卫(`RequirePerm` / `PermissionGuard`) |
| `chat/` | 对话代理:转发到 ai-service(流式直转);管理用户当前模型 |
| `users/` | 用户/部门/职级/权限点/两维权限绑定/审计查询;**业务规则引擎**唯一实现 |
| `audit/` | 审计日志 |
| `files/` | 文件相关 |

关键约定:ai-service 的工具**读直连 MySQL、写走 NestJS 内部 HTTP**(X-Service-Key),
保证业务规则只在 NestJS 实现一次(但当前 Agent 工具组已移除,仅保留通用工具)。

## 四、ai-service(Agent 编排,6010)

### 入口与路由(`app/main.py`)

- `POST /v1/chat/completions`:`preprocess()`后分流——Agent 路径 / 直答路径;
- 会话持久化 `/v1/conversations/*`;文档上传与 RAG 检索 `/v1/documents`、`/v1/rag/search`;
- 内部鉴权 `require_service_key`:只信任 NestJS 转来的请求。

### 业务装配(`app/agent.py`,薄)

当前 Agent = 基础工具 + (有 embed 配置时)RAG 检索工具。旧仓库工具组(`app/assets.py`)、
用户权限工具组(`app/users_tools.py`)与入口守门子图(`app/guardrail.py`)已移除。

### 工具与支撑模块

| 文件 | 内容 |
|---|---|
| `app/tools/base.py` | 静态工具:天气/计算器/当前时间/公交 |
| `app/tools/rag.py` | `search_docs`:RAG 检索工具 |

## 五、model-gateway(Java,模型出口网关,6015)

| 包 | 作用 |
|---|---|
| `auth/` | 解析 NestJS JWT;`PermissionService` 按 users 表 + job_level_permissions / user_permissions 解析有效权限码;`AuthInterceptor` 按 `@RequirePermission` 校验 |
| `perm/` | 只读实体:permissions / job_level_permissions / user_permissions |
| `invoke/` | 模型调用入口 + 调用日志 |
| `ratelimit/` | 限流 / 熔断策略 |
| `repo/` | 渠道管理 |
| `stats/` | 调用统计看板 |
| `user/` | 用户查询(只读) |

已移除团队管理包(`team/`)与团队相关表;用户表只读共享 NestJS users,不再持有 role/permission,
改由 `isSuperAdmin` + 有效权限码控制。

## 六、权限模型(2026-08 重构)

用户身份 = `isSuperAdmin` + `jobLevelId` + `departmentId` + `deptPosition`。

有效权限码(与 model-gateway 同一规则):
- 超管 → 全部 5 个权限点;
- 否则逐权限点:个人绑定有记录则以 `allowed` 为准(允许/拒绝);
  无个人绑定则继承职级绑定;职级也未绑定则无权限。

5 个可配置权限点:

| code | 名称 | 管控落点 |
|---|---|---|
| `dept:member` | 部门成员管理 | NestJS `/v1/users` 写操作(+上级管下级) |
| `dept:info` | 部门信息维护 | NestJS `/v1/departments` 写操作 |
| `dept:knowledge` | 部门知识库管理 | 预留,待知识库功能落地 |
| `log:view` | 日志权限 | model-gateway `/api/logs` |
| `policy:manage` | 限流熔断权限 | model-gateway `/api/policies` |

部门职位名额(仅 NestJS 用户管理/转岗/职位调整时校验):
- 经理(MANAGER):每部门 1 名
- 副经理(DEPUTY):每部门 2 名
- 组长(LEADER)、组员(MEMBER):不限

用户管理遵循职级上下级:操作者职级必须**严格高于**目标用户职级,且目标部门
在操作者部门子树内;超管不受此限。
